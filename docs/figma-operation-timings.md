# Замеры операций Figma Local Bridge

Первый этап диагностики задержек: ответы операций содержат `timings` в
`structuredContent` и в текстовом JSON. Замеры не добавляют вызовов Figma,
логирования, повторных попыток или новых тайм-аутов. Часы монотонные
(`performance.now()`), длительности указаны в миллисекундах.

Это измерение отдельных участков исполнения, **не время всей задачи агента**.
Работа модели, доставка запроса до MCP, сериализация и доставка ответа клиенту
не входят в `totalMs`.

## Формат

Условный пример (не результат живого замера):

```json
{
  "timings": {
    "version": 1,
    "scope": "bridge_operation",
    "operation": "patch_nodes",
    "totalMs": 50,
    "stages": [
      { "name": "resolveTarget", "durationMs": 10, "status": "ok" },
      { "name": "execute", "durationMs": 30, "status": "ok" }
    ]
  }
}
```

`totalMs` включает промежутки между этапами, поэтому может быть больше их суммы.
Округление до 0,001 мс может дать небольшую погрешность при сложении.
В `stages` входят только начатые этапы. Отсутствие этапа не означает нулевую
длительность. `status: "error"` фиксирует исключение на этапе, но не определяет,
были ли изменены узлы: для этого остаётся `operationStatus`.

## Границы измерения

| Область | Что входит | Что исключено |
| --- | --- | --- |
| `bridge_operation` | От входа в `runToolOperation` до формирования ответа | Предварительная проверка аргументов, генерация кода, начальный discovery в `inspect_selection` |
| `reconstruction_handler` | От входа в `recreateScreen`, включая проверку аргументов и подготовку сборки, до формирования ответа | Проверка входной схемы самим MCP SDK до вызова обработчика |

`get_status`, ошибки до входа в эти функции и ответ выбора файла без чтения
холста не содержат этих замеров. Не сравнивайте разные `scope` как одинаковые
измерения полного MCP-вызова.

| Этап | Что измеряется |
| --- | --- |
| `resolveTarget` | Подготовка и выбор подключения через `runInFile`; это не отдельный замер очереди broker |
| `execute` | Полный вызов Bridge для обычной операции: транспорт, очередь, проверки готовности и Plugin API вместе |
| `screenshot` | Получение PNG через Bridge, включая транспорт, очередь и проверки готовности |
| `validate` | Проверка аргументов внутри `recreateScreen` |
| `readSource` | Генерация команды и полное чтение исходника через Bridge, включая нужные ресурсы и шрифты |
| `compile` | Преобразование прочитанного исходника и изменений в спецификацию |
| `preflight` | Генерация и исполнение dryRun при воссоздании |
| `write` | Генерация и исполнение сборки при воссоздании, включая встроенные проверки результата |

Время шрифтов, очереди и самого Plugin API пока не разделено: оно входит в
соответствующий этап Bridge. При тайм-ауте фиксируется время до получения ошибки,
а не время фактического завершения продолжающейся операции в Figma.

## Как получить первые данные

1. Переподключить MCP `figma-local`, чтобы он загрузил обновлённые исходники.
   Для этой правки сборка Figma-плагина и код broker не менялись.
   Если Codex использует установленную копию в кэше, сначала обновить её штатной
   установкой плагина; одного переподключения старой копии недостаточно.
   `scripts/verify-codex-install.mjs` сравнивает её с исходниками проекта.
2. Проверить `get_status` с нужным `fileKey`. Устранить сообщения об устаревшем
   runtime и восстановить подключение до замеров холста.
3. На обычной разрешённой пользователем задаче сохранить ответ MCP. Существующий
   `scripts/call-tool.mjs` умеет сохранять `structuredContent` в `result.json`
   через параметр `--output`; отдельного хранилища метрик нет.
4. Сопоставить метрики с длительностью полного MCP-вызова и всей задачи из журнала
   клиента. Паузы между инструментами нельзя приписывать Bridge только по этим
   данным.
5. Для сравнения изменений использовать одинаковый исходник, действия, масштаб
   PNG, модель и уровень рассуждений. Разделять первый запуск и прогретые запуски.
   Повторные записи проводить только в отдельном разрешённом тестовом назначении.
6. Сравнить время вместе с текстами, геометрией, оформлением и поведением.
   Метрики не заменяют чтение результата, проверку PNG и прототипных переходов.

## Проверка изменения

Тесты таймера используют управляемые часы и проверяют длительности, изоляцию
параллельных запросов и сохранение исходных исключений. Тесты операций проверяют
статусы `applied`, `partial`, `unknown`, отказ экспорта, dryRun и отсутствие
повторной записи. Тестовый Figma mock не воспроизводит реальный layout engine:
полноценный замер скорости и визуальная проверка требуют подключённого файла.

ускорение. Записей в макет не выполнялось. Сырой ответ сохранён локально в
`/tmp/figma-timings-live-read/result.json` (временный файл, не часть репозитория).
